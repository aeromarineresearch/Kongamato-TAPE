KongamatoTape — a stacked energy tape for speed and height awareness

This demonstrator implements an expanding energy tape. The main bar is a height bar graph: it grows from zero at the left to the current height at its leading right edge, where the altitude number sits. A smaller airspeed bar floats at that same leading edge, with the airspeed number held a fixed gap to its left — so airspeed reads on top, height on the bottom, and the two never swap places. As height changes both readouts travel together and keep their spacing; they collapse into a vertical stack only when both values are too low to separate — on the ground, parked.

The height bar tracks MSL altitude, so it holds steady as terrain rises and falls beneath the aircraft — it does not jitter with every ridge. Terrain threat instead appears as a heatmap that grows inward from the leading edge: amber as clearance nears the safety floor, deepening to red below it. If the pilot lets it descend through the floor, a terrain-following autopilot engages, holding a hard-deck clearance (~800 ft AGL) and climbing the terrain — and only in that mode does the bar track the ground, until the pilot recovers or the ridge falls away. The airspeed bar runs a gradient through its own band (blue → amber → red for cruise / caution / never-exceed).

The core insight is sound

Fixing each metric to a constant screen region is a legitimate human-factors principle: a stable spatial mapping lets a pilot read a value pre-attentively, without re-parsing the layout under load. Freezing airspeed-above / height-below removes the value-flipping hazard the original sketch set out to solve. That part is a real improvement over any layout where the two can swap places.

What the "energy index" actually is

The intuition that "both bars long = high total energy" is exactly right, and it has a precise name. An aircraft's total mechanical energy per unit weight is its specific energy, or energy height:

hₑ = h + V² / 2g   [feet]

where h is height, V is true airspeed, and g is gravitational acceleration. Height is potential energy; speed squared is kinetic energy; hₑ is the altitude you could reach if you traded all your speed for climb. This is the foundation of energy–maneuverability theory (Boyd & Christie, 1960s) and is the rigorous, quantitative version of the "energy bar." It's computed live in the tile marked hₑ above, and the 2-D envelope plot is really a map of energy states: the dangerous corner is bottom-left — low, slow, and out of energy to trade.

What a reviewer will push back on

To be useful to professionals, the concept has to survive the critique they'll actually give. Here are the substantive ones, with how this build responds.

1. It fights a strong population stereotype

Certified EFIS/PFD layouts use vertical moving tapes — airspeed left, altitude right — because "up = more / higher" is a deeply trained spatial reflex, and a moving tape encodes rate through motion. A horizontal height bar where "higher = further right" sacrifices that. The strongest defense of your layout is to position it as a supplemental energy-awareness strip beside a conventional scan, not a replacement for the primary altimeter.

2. A single marker loses trend

Moving tapes show how fast a value is changing. A dot on a static bar does not. This build recovers part of that with a live vertical-speed tile and a 6-second trail on the envelope plot, so energy trend is visible. A production version should add short trend vectors on the tape markers.

3. Color alone is not enough

Roughly 8% of men have a color-vision deficiency, so alert state must never be carried by hue alone. This build uses aviation-standard green/amber/red plus luminance (safe states are dim, hazards are bright — the "dark cockpit" philosophy), plus marker position, plus the numeric text, and the envelope draws boundary contours at Vs, Vno, Vne and the terrain floor. Redundant coding is a requirement, not a polish item.

4. Non-linear where it matters. Danger is not linearly distributed along the scale — resolution should expand near the stall and near the terrain floor. A linear tape wastes pixels in the safe cruise band. This is the single biggest refinement to make before flight test.

5. Alerting discipline

A background that "goes wild" invites distraction and startle. This build keeps the field quiet in the safe band and only escalates on genuine exceedance, and it honors prefers-reduced-motion to suppress flashing. Alerts should be earned, not ambient.

Telemetry & hardware — a corrected reference

The AI notes you were sent contain several errors that an avionics engineer would flag immediately. The architecture (Matek/ArduPilot flight controller streaming MAVLink over UART into a compute core driving a display) is reasonable. The data plumbing details are not. Corrections:

Claim in the notesReality
VFR_HUD.airspeed is "already in knots" It is always metres/second. Multiply by 1.94384 for knots. Same for altitude: VFR_HUD.alt is metres MSL. wrong
GPS_RAW_INT.alt gives AGL It is MSL (millimetres), and GPS vertical is noisy. AGL is never GPS altitude. Mislabeling this in a terrain-warning system is dangerous. wrong
GLOBAL_POSITION_INT.relative_alt = height above ground It is height above the home/arming point, not above the terrain beneath you. Different thing entirely. wrong
AGL source Use TERRAIN_REPORT.current_height (terrain-database AGL), a downward RANGEFINDER/DISTANCE_SENSOR, or the EKF terrain estimate. correct approach
Rust serialport code (SerialPortSettings, prelude) That's the 3.x API. In 4.x it's serialport::new(path, 115200).timeout(..).open(). The sample will not compile. won't build
mavlink::read_v2_msg returns a "reader," and e.kind() on read errors It returns a decoded message, not a reader; use mavlink::connect() then recv(). Read errors are MessageReadError, not io::Error — match the Io(..) variant first. won't build
Flash ArduPilot with Betaflight Configurator No. ArduPilot is flashed with Mission Planner or QGroundControl. Betaflight Configurator flashes Betaflight/INAV. wrong
SERIALx_PROTOCOL=2, SERIALx_BAUD=115 Correct — protocol 2 is MAVLink2 and ArduPilot's baud code 115 means 115200. correct
"Python is too slow… garbage-collection micro-stutters" Overstated. Parsing MAVLink at 10–20 Hz is trivial in any language; CPython is reference-counted. Rust is a fine choice for other reasons (control, footprint, safety), but not because of GC pauses in the parser. half-true
ESP32 can't drive a 10-inch high-res panel over SPI Fair. SPI bandwidth is the limit; a Pi CM4 / SBC with a proper display bus (or RGB/MIPI) is the right call for that size. correct

Bottom line on the notes: the hardware shopping list and the high-level topology are reasonable; the MAVLink field semantics, the units, the AGL source, and both Rust code samples are wrong or won't compile. Treat the prose as a starting point and verify every field against the MAVLink common message set and the current crate docs.
